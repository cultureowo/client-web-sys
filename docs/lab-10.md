# Лабораторна №10 — як захищати Study Planner із REST API

## 1. Що ми зробили

Коротка відповідь, яку можна сказати на початку:

> У цій лабораторній я підключила Study Planner до REST API DummyJSON. Винесла HTTP-запити в окремий клієнт, а операції із завданнями — в repository. Додала серверну пагінацію, окреме завантаження деталей, асинхронні CRUD-операції, обробку loading/error/empty/success та скасування GET-запитів через AbortController.

У №9 список був локальним і зберігався в localStorage. Тепер початкові дані завантажуються з API; localStorage використовується тільки для активного фільтра. Context і reducer залишилися там, де допомагають керувати станом.

## 2. Підготовка перед захистом

1. Перевір Node.js: `node --version`, потрібна версія 22.22+.
2. Встанови залежності: `npm ci`.
3. Перевір наявність `.env`: `VITE_API_URL=https://dummyjson.com`. Зразок — [`.env.example`](../.env.example). Якщо `.env` немає, у PowerShell виконай `Copy-Item .env.example .env`.
4. Запусти `npm run dev` і відкрий адресу з термінала. Після зміни `.env` сервер потрібно перезапустити.
5. Для підготовки чистого сценарію натисни «Скинути зміни», обери «Усі» й очисть пошук.
6. Відкрий DevTools → Network → Fetch/XHR. За потреби очисть журнал запитів.

Якщо PowerShell забороняє `npm.ps1`, використовуй `npm.cmd`.

Команди перевірки: `npm run lint`, `npm test`, `npm run build`. Вони мають завершуватися без помилок.

## 3. Демонстрація в браузері — приблизно 5–7 хвилин

### Крок 1. Список і пагінація

Покажи отриманий список, номер сторінки та кнопки «Наступна» / «Попередня». Перейди на наступну сторінку.

Скажи:

> Завдання приходять із сервера частинами по 10. Для першої сторінки skip дорівнює 0, для другої — 10. Кількість сторінок обчислюється з total у відповіді API.

У Network покажи GET `/todos?limit=10&skip=0` і GET зі `skip=10`. Відповідь містить `todos`, `total`, `skip`, `limit`. Не запам’ятовуй фіксовану загальну кількість: вона береться із сервера.

### Крок 2. Деталі завдання

Натисни іконку ока біля **завдання, завантаженого з API**. Покажи назву, опис, категорію, пріоритет і стан. У Network з’явиться GET `/todos/:id`.

> Деталі завантажуються окремим запитом. Результат зберігається локально у TaskDetails, а не дублюється у глобальному Context.

Опис відсутній в API — тому для незмінених завдань показується «Опис не додано». Пріоритет і категорія отримують значення за замовчуванням під час mapping.

Закрий деталі кнопкою або Escape.

### Крок 3. Створення

Введи назву, опис, категорію й пріоритет. Натисни «Додати завдання».

Покажи POST `/todos/add`, нове завдання, очищення форми та success Toast.

> Форма очікує результат асинхронної операції через await. Вона очищується тільки після успішної відповіді. Якщо запит завершиться помилкою, введені поля залишаться.

У POST надсилаються тільки поля контракту: `todo`, `completed`, `userId`. Опис, пріоритет, категорія та колір залишаються metadata клієнта.

### Крок 4. Оновлення

Для демонстрації HTTP вибери **існуюче серверне завдання**, а не щойно створене сесійне.

Натисни «Редагувати», зміни назву, збережи. У Network покажи PATCH `/todos/:id`. Можна також перемкнути checkbox — це теж PATCH.

> UI оновлюється тільки після успіху запиту. Це звичайне, не optimistic, оновлення. На час операції повторні зміни заблоковані.

### Крок 5. Видалення

Натисни «Видалити». Спочатку з’явиться запит підтвердження. Натисни «Підтвердити видалення»: почнеться п’ятисекундний Undo-таймер із прогресом. Натисни «Скасувати» й покажи, що DELETE не надсилався.

Повтори, підтвердь і дочекайся завершення таймера. У Network покажи DELETE `/todos/:id`, після успіху завдання зникне.

> До завершення Undo запит не надсилається. Після завершення таймера викликається repository.delete. Якщо HTTP-запит завершується помилкою, завдання залишається в списку.

Масове очищення виконаних працює на поточній сторінці з тим самим підтвердженням і Undo. Записи видаляються послідовно. Якщо одна операція не вдалася, раніше успішно видалені записи не повертаються, а невидалені залишаються для повторної дії.

### Крок 6. Loading, error, empty, success

| Стан    | Як показати                                           |
| ------- | ----------------------------------------------------- |
| Loading | У Network увімкни Slow 3G та натисни «Оновити список» |
| Error   | Увімкни Offline та повтори завантаження               |
| Retry   | Поверни No throttling, натисни «Спробувати ще»        |
| Empty   | Введи в пошук текст, якого немає на поточній сторінці |
| Success | Створи або відредагуй завдання, покажи Toast          |

Помилки завантаження списку й деталей мають окремі кнопки повторення. Помилки мутацій показуються у Toast і біля списку; повторити можна тією самою дією. Повідомлення не використовують `alert()`.

### Крок 7. Скасування GET

Залиш Slow 3G, швидко натисни «Наступна» двічі. Попередній GET має бути canceled, а остання обрана сторінка — відображатися коректно. Також відкрий деталі й одразу закрий: їхній GET скасується.

> AbortController скасовує непотрібний запит. Cleanup Effect викликає abort, а перевірка signal.aborted не дозволяє застарілій відповіді змінити state. Скасування не показується як звичайна помилка.

Після демонстрації поверни No throttling.

## 4. Важливе обмеження навчального API

Це потрібно пояснити впевнено:

> DummyJSON лише симулює POST, PATCH і DELETE. Він повертає відповідь, але не зберігає зміни назавжди. Тому після успішної мутації я оновлюю стан React, а після перезавантаження знову отримую початкові серверні дані. Це обмеження сервісу, передбачене лабораторною.

Подробиці реалізації:

- Успішні зміни існуючих завдань записуються в сесійний журнал `changes` у reducer. Вони застосовуються поверх повторних відповідей API й не губляться при пагінації.
- API може повертати той самий ID на кілька POST. Нові записи отримують `session:UUID`, тому React keys не конфліктують.
- Нові записи показуються на першій сторінці, понад її серверні 10 елементів.
- На сервері створених записів фактично немає. Repository обробляє їхні подальші деталі, редагування та видалення в поточній сесії без неможливих GET/PATCH/DELETE за фальшивим ID.
- Для демонстрації реального GET за ID, PATCH і DELETE використовуй серверні завдання без позначки «Створено в поточній сесії».
- Metadata `description`, `priority`, `category`, `categoryColor` не підтримуються API, тому залишаються клієнтськими.
- Після перезавантаження або «Скинути зміни» сесійні створення/редагування/видалення скидаються. «Оновити список» тільки повторює GET, зберігаючи журнал сесії.
- Пагінація рахується за серверним total. Фільтри, пошук, сортування та статистика працюють у межах поточної сторінки; це явно вказано в UI.

## 5. Порядок показу коду

### 5.1. Конфігурація й точка входу

Покажи [`.env.example`](../.env.example), [`main.tsx`](../src/main.tsx) та [`App.tsx`](../src/App.tsx).

> URL сервісу знаходиться в environment variable VITE_API_URL. Vite надає його через import.meta.env. TaskProvider огортає App. App збирає компоненти сторінки та не містить fetch чи URL endpoint-ів.

`.env` виключений із Git, `.env.example` містить лише публічний приклад. VITE-змінні потрапляють у клієнтський застосунок, тому це не місце для секретів.

### 5.2. HTTP client

Відкрий [`src/api/httpClient.ts`](../src/api/httpClient.ts).

Покажи `createHttpClient`, побудову URL, `fetch`, `response.ok` і `ApiError`.

> HTTP client відповідає за транспорт: базовий URL, заголовки, виконання запиту, перевірку HTTP-статусу й читання JSON. Він не знає, як виглядає компонент або Task.

Ключовий фрагмент:

```ts
const response = await fetch(url, { ...options, headers });
if (!response.ok) {
  throw new ApiError(/* зрозуміле повідомлення */, response.status);
}
```

> Fetch не вважає статус 404 або 500 відхиленим Promise. Тому перевірка response.ok обов’язкова. Окремо обробляються неправильний JSON і відсутня конфігурація.

`errorMessage` централізовано перетворює помилки на зрозумілі повідомлення. `isAbortError` відрізняє скасування запиту від звичайної помилки.

### 5.3. Repository

Відкрий [`src/repositories/taskRepository.ts`](../src/repositories/taskRepository.ts).

> Repository приховує endpoint-и та формат даних API. Код, який керує інтерфейсом, просить getAll або update, а не будує HTTP-запит самостійно.

| Метод repository                    | HTTP                | Призначення              |
| ----------------------------------- | ------------------- | ------------------------ |
| `getAll({ limit, skip, signal })`   | GET `/todos?...`    | Сторінка завдань         |
| `getById(id, signal, sessionTask?)` | GET `/todos/:id`    | Деталі серверного запису |
| `create(draft, signal)`             | POST `/todos/add`   | Створення                |
| `update(task, changes, signal)`     | PATCH `/todos/:id`  | Назва й completed        |
| `delete(task, signal)`              | DELETE `/todos/:id` | Видалення                |

Для сесійних записів є описаний вище локальний шлях, оскільки вони не існують на сервері.

### 5.4. DTO та domain model

Покажи [`types/api.ts`](../src/types/api.ts), [`types/task.ts`](../src/types/task.ts) і `toTask` у repository.

> DTO — формат відповіді API: id, todo, completed, userId. Domain Task — модель мого інтерфейсу: title, description, priority, category та інші поля. Mapping перетворює todo на title, числовий id на рядок і задає значення додаткових полів.

Приклад:

```ts
{
  id: String(todo.id),
  title: todo.todo,
  completed: todo.completed,
  description: "",
  priority: "medium",
  category: "Загальне",
  // ...
}
```

Repository також перевіряє структуру відповіді під час виконання. Сам TypeScript не перевіряє JSON, який прийшов із мережі.

### 5.5. Завантаження та скасування

Відкрий [`hooks/useTasks.ts`](../src/hooks/useTasks.ts).

Покажи Effect із залежностями `[page, revision]`:

```ts
const controller = new AbortController();
taskRepository.getAll({
  limit: PAGE_SIZE,
  skip: (page - 1) * PAGE_SIZE,
  signal: controller.signal,
});
return () => controller.abort();
```

> Коли змінюється page або користувач повторює запит через revision, запускається нове завантаження. Cleanup скасовує попереднє. Результат записується у reducer тільки якщо запит ще актуальний.

Покажи `runMutation`:

> Ця функція встановлює стан виконання, блокує паралельний повторний запис, очікує операцію та обробляє помилку. State оновлюється лише після успішної відповіді. Мутації також отримують сигнал, який скасовується при unmount.

У StrictMode під час розробки можна побачити додатковий цикл Effect і скасований початковий GET. Це перевірка коректності cleanup, а не причина прибирати StrictMode.

### 5.6. Reducer та Context

Відкрий [`reducers/taskReducer.ts`](../src/reducers/taskReducer.ts), потім [`context/TaskProvider.tsx`](../src/context/TaskProvider.tsx).

> Reducer зберігає стан поточної сторінки: loading/success/error, відповідь сервера і журнал успішних змін сесії. Він залишається чистим: без fetch, localStorage або таймерів. Видимі tasks обчислюються з цього стану функцією selectPageTasks.

Actions: `load`, `loaded`, `failed`, `upsert`, `deleted`, `reset`.

> TaskProvider поєднує useTasks зі станом інтерфейсу: фільтром, пошуком, редагуванням, selectedId, Toast і підтвердженням/Undo. Context лише надає доступ до результатів hook; він не створює незалежну копію server state.

### 5.7. Форма та деталі

Відкрий [`TaskForm.tsx`](../src/components/TaskForm.tsx): локальні поля, `async submit`, `await`, очищення тільки після `success`.

Потім [`TaskDetails.tsx`](../src/components/TaskDetails.tsx): локальний async state, окремий repository.getById, кнопка Retry, AbortController і cleanup. Сам компонент не містить endpoint-ів чи fetch.

### 5.8. Додаткові можливості

Покажи [`useDebouncedValue.ts`](../src/hooks/useDebouncedValue.ts): таймер 300 мс і clearTimeout у cleanup. Пошук локальний на поточній сторінці, без вигаданого server search endpoint.

Централізована нормалізація помилок — `errorMessage` у HTTP layer. Optimistic update та Axios не використовуються: у роботі обрано fetch і оновлення після підтвердження сервера.

## 6. Server state та UI state

| Server/data state                        | Client/UI state                   |
| ---------------------------------------- | --------------------------------- |
| Поточна відповідь списку й total         | Номер сторінки                    |
| Результати підтверджених мутацій у сесії | Фільтр, пошук, сортування         |
| Loading/error завантаження               | Поля форми, editingId, selectedId |
| Відповідь деталей, локальна для діалогу  | Тема, Toast, підтвердження й Undo |

Журнал сесії потрібний саме через непостійність DummyJSON; він не записується у localStorage. Старий ключ завдань із №9 не використовується. Відфільтрований список і статистика обчислюються під час render, а не через додатковий state/effect.

## 7. Короткі відповіді на всі контрольні запитання

1. **Що таке REST API?** Інтерфейс роботи з ресурсами через HTTP: ресурс має адресу, а метод запиту визначає операцію. У цій роботі ресурс — todo, відповіді — JSON.
2. **GET / POST / PUT / PATCH / DELETE?** GET читає, POST створює, PUT зазвичай замінює представлення ресурсу, PATCH частково змінює, DELETE видаляє. Конкретний контракт визначає API; тут оновлення реалізоване через PATCH.
3. **Навіщо виносити API-логіку?** Щоб компоненти відповідали за інтерфейс, а транспорт, помилки й формат відповіді можна було змінювати та тестувати окремо.
4. **Repository Pattern?** Шар доступу до даних, який надає операції предметної області й приховує спосіб отримання/збереження даних.
5. **Відповідальність нашого repository?** Endpoint-и todos, DTO mapping, перевірка відповіді, getAll/getById/create/update/delete та особливості сесійних записів DummyJSON.
6. **Client проти repository?** HTTP client знає про URL, fetch, заголовки й статуси. Repository знає про Task, todo та потрібні операції.
7. **Які async states?** Loading, success, error та empty як успішний результат без записів. Для мутацій також потрібні busy-стан і повідомлення про результат.
8. **Server проти UI state?** Server state приходить із зовнішнього джерела й може бути неактуальним. UI state описує взаємодію користувачки: сторінку, фільтр, форму, відкритий діалог.
9. **Чому не дублювати server state у localStorage?** Копія може застаріти та конфліктувати з API. Потрібні окремі правила кешування; у цій роботі localStorage містить лише фільтр.
10. **AbortController?** Створює AbortSignal для скасування асинхронного запиту. `abort()` зупиняє непотрібне очікування та запобігає застарілому оновленню UI разом із перевіркою сигналу.
11. **Що при unmount під час запиту?** Сам fetch автоматично не прив’язаний до життя компонента. Наш cleanup викликає abort; результат скасованого запиту не записується у state.
12. **Fetch проти Axios?** Fetch вбудований у браузер і потребує ручної перевірки response.ok. Axios — окрема бібліотека з власними налаштуваннями, перетвореннями та типовим відхиленням Promise для невдалих HTTP-статусів. Обидва можуть працювати з AbortSignal; ми використали fetch.
13. **Optimistic update?** UI змінюється до відповіді сервера, а при помилці потрібне повернення попереднього стану. У нас зміна застосовується після успіху, тому rollback не потрібний.
14. **Чому після POST не потрібне перезавантаження?** Успішна відповідь дозволяє додати запис до React state, після чого React оновить UI. Для DummyJSON перезавантаження ще й втратить сесійні зміни.
15. **Як обробити HTTP-помилку?** Перевірити response.ok, кинути типізовану помилку, перехопити її вище, показати зрозумілий error state та можливість повторити. Abort обробляється окремо; невдалу мутацію не видаємо за успішну.

## 8. Шпаргалка перед захистом

| Запитання викладача              | Де показати                                                       |
| -------------------------------- | ----------------------------------------------------------------- |
| Де адреса API?                   | `.env.example` → `httpClient.ts`                                  |
| Де викликається fetch?           | Тільки `api/httpClient.ts`                                        |
| Де endpoint-и?                   | `repositories/taskRepository.ts`                                  |
| Де перетворюється todo на title? | `toTask` у repository                                             |
| Де пагінація?                    | `useTasks.ts`: limit, skip; `Pagination.tsx`                      |
| Де скасування GET?               | Cleanup у `useTasks.ts` і `TaskDetails.tsx`                       |
| Де loading/error/retry?          | `TaskList.tsx`, `RequestState.tsx`, `TaskDetails.tsx`             |
| Де POST і очищення форми?        | `TaskForm.tsx` → Context → `useTasks.create` → repository         |
| Де PATCH?                        | `taskRepository.update`                                           |
| Де підтвердження DELETE?         | `Toast.tsx` → `TaskProvider` → `useTasks.remove`                  |
| Чому після reload зміни зникли?  | DummyJSON не зберігає мутації; UI показує результати лише в сесії |

Фраза, що описує основний рух даних:

> Компонент викликає операцію Context, useTasks керує асинхронним станом, repository формує операцію над Task, HTTP client виконує запит. Після успіху reducer оновлює дані, і React повторно відображає інтерфейс.

## 9. Що перевірено

- ESLint і TypeScript/production build.
- 16 автоматичних тестів: HTTP URL/headers/status/JSON/abort; DTO mapping, payload CRUD, сесійні ID, помилки repository; reducer, застарілі сторінки, повторне завантаження; безпечне читання сховища.
- У браузері з реальним DummyJSON: список, GET деталей, пагінація, POST, PATCH, completed, DELETE, збереження сесійних змін між сторінками.
- Контрольовані збої відповідей у браузерному тесті: retry списку/деталей, невдалий POST без очищення форми, невдалий PATCH без зміни запису, невдалий DELETE без видалення.
- Затримані GET у браузерному тесті: перехід на нову сторінку та закриття деталей скасовують попередні запити.
- Підтвердження та Undo: HTTP DELETE не надсилається, якщо дію скасували до завершення таймера.
