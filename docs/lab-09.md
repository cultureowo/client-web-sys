# Лабораторна №9: пояснення для захисту

## Що показати у коді

1. `main.tsx`: TaskProvider огортає App, усі вкладені компоненти можуть читати Context.
2. `TaskContext.ts`: createContext та тип API; `useTaskContext.ts`: useContext і зрозуміла помилка поза Provider.
3. `TaskProvider.tsx`: useReducer, lazy initializer зі сховища, функції для операцій. Tasks не дублюються у useState чи useLocalStorage.
4. `taskReducer.ts`: типізовані actions та чисті immutable updates через map, filter і spread.
5. `TaskForm.tsx`: локальний стан полів, перевірка назви, створення/редагування через API Context. Key форми перемонтовує її при зміні редагованого завдання.
6. `TaskItem.tsx`: task надходить через props, але actions беруться з Context без передачі через TaskList.
7. Effects: збереження завдань, таймер видалення, автозакриття Toast, синхронізація document.title.
8. `useLocalStorage.ts`: generic hook використаний для активного фільтра.
9. `Toast.tsx`: власний компонент, Undo та CSS-прогрес; звичайні повідомлення зникають через 4 секунди.

## Послідовність Undo

requestDelete → dispatch → reducer записує pending із ID, токеном і часом → Effect запускає таймер → TaskItem показує «Буде видалено», Toast — прогрес.

Undo → pending стає null → cleanup викликає clearTimeout → завдання залишається. Після 5 секунд без Undo Effect dispatch-ить confirmDelete, reducer видаляє завдання, Effect синхронізації зберігає новий масив.

Масове очищення використовує групу ID й той самий механізм. Reset очищає pending і повертає початкові дані. Перезавантаження зберігає завдання з незавершеним видаленням, оскільки pending не записується у localStorage.

## Контрольні запитання

1. **Підняття state:** потрібне, коли кілька компонентів користуються одними даними; стан переносять у спільного батька або Provider.
2. **Prop drilling:** передавання даних через проміжні компоненти. Context дозволяє вкладеним споживачам отримувати спільне значення без цих проміжних props.
3. **Reducer:** функція `(state, action) => nextState`, яка централізує правила пов’язаних оновлень.
4. **Чистий reducer:** однакові аргументи дають однаковий результат; немає мутацій аргументів, DOM, таймерів, випадкових ID або запису в сховище.
5. **Action і dispatch:** action описує подію й дані, dispatch передає цю команду в чергу оновлення reducer.
6. **Коли useReducer:** коли є кілька пов’язаних операцій і переходів стану. Прості поля форми зручно залишити у useState.
7. **Context API:** createContext, Provider із value, споживання через useContext.
8. **Чи весь state у Context:** ні, локальні поля й налаштування залишаються біля UI, якому вони потрібні.
9. **Side effect:** взаємодія із зовнішньою системою — сховищем, таймером, document.title, мережею.
10. **useEffect:** синхронізує React із зовнішньою системою після commit.
11. **Effect і cleanup:** setup запускається після першого commit і при зміні залежностей. Попередній cleanup — перед новим setup та під час unmount. StrictMode у розробці додатково перевіряє setup/cleanup.
12. **localStorage — side effect:** це зовнішнє для React сховище; запис змінює браузер і може завершитися помилкою.
13. **Таймер поза reducer:** він залежить від часу, запускає зовнішню дію й потребує cleanup, а reducer лише обчислює новий стан.
14. **clearTimeout:** не дозволяє скасованій чи застарілій операції видалити дані пізніше.
15. **Derived state:** статистика та видимий список обчислюються з tasks; дублювання у state створює ризик розсинхронізації.
16. **Custom Hook:** функція з префіксом use, що використовує hooks для повторного застосування логіки. Кожен виклик має власний стан, якщо hook не читає спільний Context.
17. **Правила hooks:** викликати на верхньому рівні компонента або custom hook, не в умовах, циклах чи звичайних обробниках. Вказувати залежності effects та cleanup ресурсів.

## Перевірки

`npm test`: незмінність даних, add/toggle/update, Undo, старий токен, масове видалення, reset, відсутній/пошкоджений JSON, порожній масив і недоступне сховище. `npm run lint`: ESLint. `npm run build`: TypeScript і production-збірка.

Для ручної перевірки пошкоджених даних у DevTools → Application → Local Storage замініть `study-planner.tasks.v1` на некоректний JSON і перезавантажте: має з’явитися початковий список. Запустіть видалення й одразу перезавантажте: завдання має залишитися.
